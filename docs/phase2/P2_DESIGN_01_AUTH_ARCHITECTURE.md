## 2. Trust-boundary architecture

```text
React browser (untrusted)
  ├── Firebase Web Google popup -> Firebase ID token -> auth exchange only
  ├── native custom email/password and verification UI
  ├── access JWT: ephemeral JavaScript memory, Authorization Bearer only
  └── refresh cookie: host-only Secure HttpOnly; signed session CSRF cookie readable to JS
             │ HTTPS same-origin /api/v1
             ▼
Cloudflare Pages Function (preferred candidate; thin proxy; secret-authenticated upstream)
             │ HTTPS to Render
             ▼
Express modular API -> auth/origin/CSRF/abuse middleware -> identity service
             ├── Firebase Admin verifier
             ├── Argon2id bounded worker capacity
             ├── EmailSender (local mock / gated Brevo HTTPS)
             ├── SmsSender (development mock / paid real SMS only by explicit exception)
             └── Signed app JWT + rotating, DB-backed refresh session
             │
             ▼
MongoDB Atlas Free authoritative:
  pendingRegistrations, users, authIdentities, sessions,
  verificationChallenges, reauthTickets, authRateLimits,
  emailSendBudget, securityAuditEvents, registrationAllowlist
```

**Fallback deployment** already exists in the roadmap: Express serves the compiled SPA and `/api` from one Render HTTPS origin. The choice between these approved deployment candidates is based on security/cookie/latency/quota tests. **Do not bypass the ingress proof** by exposing unprotected direct Render auth endpoints. Firebase tokens never serve as API Bearer tokens, and the proxy is never a source of the user's role or subscription.

## 3. Registration and identity proof — corrected invariant

### 3.1 Never activate an attacker's pending password

An unverified address does **not** create a durable `users` or `authIdentities` row. Only `pendingRegistrations` holds the temporary Argon2id credential, pre-registration metadata, OTP digest, random registration ID, and digest of a browser-bound registration nonce. `pendingRegistrations.emailNormalized` is unique, TTL-limited and CAS-replaceable **only after a 60-second per-email replacement cooldown and combined register/resend 3-per-15-minute durable per-email budget; a rejected replacement cannot erase another active registration**. A later registration for the same unverified email replaces the earlier attempt, resets proof material and makes old attempts unusable. Existing verified users are never overwritten by registration. Both custom registration and first-use Google provisioning require the active server-issued policy identifier and consent version; append immutable `CONSENT_ACCEPTED` evidence atomically on activation/provisioning, with a server timestamp.

`POST /auth/register` returns a generic 202 with a random `registrationId` and sets a short-lived **host-only HttpOnly registration nonce cookie**, including for indistinguishable ineligible requests. `__Host-roundset_reg=reg1.<registrationId>.<nonce>` is Secure, HttpOnly, SameSite=Lax, Path=/, no Domain, Max-Age=900; registrationId uses ≥128-bit randomness and nonce ≥256-bit randomness. Only local loopback HTTP may use `roundset_reg`. Verify/resend require cookie-bound ID + nonce and strict Origin + `Sec-Fetch-Site`; they do not require app-session CSRF before an app session exists. Real pending work is stored only when admission and uniqueness allow it; no user account or app session is created. `POST /auth/verify-email` requires the `registrationId`, OTP, and matching browser nonce, checks delivery accepted and TTL, and atomically commits pending-consumption plus `users`/`authIdentities` creation within a Mongo transaction. It returns **204**, clears the registration nonce cookie, and requires a subsequent email/password login (no OTP-only auto-login). Distinct nonce cookie name from app refresh cookies.

An unverified pending registration does **not** claim the primary-user unique email; a verified Firebase Google sign-in can provision a user unaffected by unrelated pending attempts. If Google provisioning wins a race with password verification, the latter fails safely on the unique `users.emailNormalized` constraint and leaves no password identity attached. **No auto-merge** by email in either direction.

### 3.2 Established users and verified ownership

- `users._id` is stable across sessions and future interview records. `authIdentities` identifies credential owner by `(provider, subject)`; Google subject = Firebase UID, password subject = canonical email.
- Only an existing **linked** `(FIREBASE_GOOGLE,uid)` maps a Google proof to an established Roundset user. A new verified Google UID can provision a new user only after admission, canonical-email uniqueness and the above conflict rules.
- For **new Google linking in v1**, `verified Google email === users.emailNormalized` is required, along with recent step-up proving existing Roundset factor, verified provider identity and unused UID. Cross-email linking is not silently allowed. A linked Google UID remains the identity key if Google later changes its displayed email; **never silently modify canonical account/recovery email**. Surface an email-verification/profile-correction state for future managed change; do not grant password recovery to a new address implicitly.
- The `emailNormalized` policy is deterministic and single-source: trim boundary whitespace; reject CR/LF/control and non-ASCII email local/domain characters for this v1 scope; lower-case case-insensitive application login key; **never** strip Gmail dots or `+tag`. This is an intentional v1 identity-key product policy, not a universal equivalence claim about all email providers. Any internationalized-email support requires a reviewed migration.
- `users.accountStatus` is `ACTIVE|SUSPENDED|PENDING_DELETION|DELETED`. There is **no user-level `PENDING_EMAIL` state**. Deleted records omit canonical email and are tombstoned only as required by the documented privacy/audit lifecycle.

### 3.3 Registration admission

`REGISTRATION_MODE=PUBLIC|INVITE_ONLY` is checked at *new user* creation for both paths. For v1 invite-only, an operator-managed `registrationAllowlist` binds a normalized email and expiry and is atomically consumed **on verified user creation**, not merely pending signup. Existing accounts may sign in after admission closes. The ambiguous `admissionToken?` payload is removed from the Phase 2 API; Phase 10 VIP invitations are separate cryptographically expiring single-use records and never themselves login credentials.

## 4. Reauthentication and credential mutation

A successful primary-factor reauth creates an opaque **single-use** ticket scoped to `userId`, `sessionId`, `action`, optional `target`, **`methodUsed`**, `sessionEpoch` and `identityVersion`, with five-minute expiration. Store only a digest; consume conditionally in the **same transaction** as the sensitive change. Never rely on a merely signed reusable ticket.

- `POST /auth/reauth`: explicit action and optional target governed by the **closed `(action,target,methodUsed)` table in companion contracts §3.4**, enforced both on ticket issuance and consumption. `PASSWORD` step-up checks the existing password hash; `FIREBASE_GOOGLE` step-up verifies revocation, current linked UID and `auth_time <= 300 seconds` old, accepting no more than 30 seconds future skew. A refreshed Firebase ID token with fresh `iat` but stale `auth_time` is not step-up.
- `link-google`: user already has password and has freshly reauthenticated with it; **the newly linked Google ID token must also represent recent auth (`auth_time` ≤300s, ≤30s future skew)** and have an independently valid signature and canonical email match; UID must not be owned. Add identity with unique index and `identityVersion` write.
- `link-password`: user has linked Google but no password. Requires fresh Google reauth; a dedicated authenticated `/auth/identities/link-password/start` issues the purpose `LINK_PASSWORD` OTP to the canonical verified email; completion requires that code + valid ticket + new Argon2id hash. Reset and verification OTPs cannot substitute.
- `unlink`: require proof of the **remaining** factor and an action/target-bound ticket, require at least two identities in the transaction, delete only selected identity. Every credential link/unlink writes `users.identityVersion`; unlink also increments `sessionEpoch` and invalidates all app sessions. All competing link/unlink transactions contend on the **same user document**, not merely separate identity rows.
- `password/change`: a PASSWORD-method reauth ticket with action `CHANGE_PASSWORD`, plus only `newPassword`; current password is supplied at `/auth/reauth`. Its route belongs in **P2-AUTH-07a** after `/auth/reauth` exists, not P2-AUTH-03b. Atomically replace hash, increment identity version and session epoch, revoke **all** sessions, return 204 and require login. `password/reset` does the same after OTP proof without a login. No partial session continuation.
- `logout-all`: with an active bearer, immediately revoke across devices without extra step-up friction; emergency self-revocation must not be prevented by an already-compromised-factor UX.
- All recovery OTPs capture the immutable password `authIdentities._id`, `userId` and `identityVersionAtIssue`; consumption rechecks those plus active status, canonical email, exact generation and expiry **inside the same transaction** as password mutation/epoch bump. Reset OTPs issued before change/reset/unlink/deletion/email reassignment cannot mutate new credentials or a later user with the same email.
- Role/status transition and account deletion increment epoch and invalidate all sessions before any stale access can be accepted; never rely on a JWT role claim.

## 5. Session, CSRF and cryptographic lifecycle

### 5.1 Tokens and storage

- Access JWT: `jose`/Node EdDSA Ed25519 **proposed** fixed contract; `kid`, pinned `alg`, `iss`, `aud`, `sub=userId`, `sid=sessionId`, `jti`, `iat`, `exp`, `epoch`. Initial TTL 600s. Browser stores only in memory; no localStorage/IndexedDB/cookie for access. Require active user and session DB checks on protected requests; **retain immediate durable revocation even if it costs extra Atlas reads**. Instrument true operation cost before optimization. Never trust stale JWT plan/role fields.
- Refresh: opaque integrity-authenticated token `r1.<kid>.<sessionId>.<generation>.<random256bitSecret>.<mac>`. MAC domain separates version/kid/sid/gen/secret; verifier HMAC digest of the complete token (different key) stored only in `sessions.currentRefreshDigest`. Keys stored in backend secrets, never browser. `kid` selects a strictly bounded active/retiring keyring; retiring verification keys survive until the last token signed with them has expired (absolute max 30 days) or a deliberate global forced logout. **The separate refresh-digest HMAC key is also versioned and retained for old live sessions for the maximum 30-day absolute lifetime, or its deliberate replacement must trigger explicit global Roundset reauthentication. Never silently invalidate or accept old verifier digests.** Access JWT public verification keys live at least 10m + clock skew during rotations; signing keys remain private. Key loss triggers controlled forced reauthentication, not silent insecure fallback.
- Cookies on HTTPS deployment: `__Host-roundset_refresh`: `Secure; HttpOnly; SameSite=Lax; Path=/; no Domain`; `__Host-roundset_csrf`: `Secure; SameSite=Lax; Path=/; no Domain; readable by same-origin JS`. Auth response uses `Cache-Control: no-store` and **two separate `Set-Cookie` headers**. Dev unprefixed equivalents allowed only for fixed HTTP loopback, never production.
- Candidate refresh and CSRF cookies get the **same seven-day sliding idle** expiry (bounded by absolute 30d session lifetime); ADMIN sessions receive 12h idle / 24h absolute, and **both cookies use the same shorter remaining idle/absolute bound**; candidate refresh absolute session max 30 days, even with rotation. Issue/reissue both at login and every successful refresh; clear both on logout. CSRF `c1.<kid>.<sid>.<nonce>.<mac>` binds to the specific active session, verified with HMAC, same cookie/header value and constant-time comparisons. Cookie expiry is aligned; no promise of perpetual refresh after browser deletes cookies.

### 5.2 Rotation and revocation

1. Strictly verify allowed Origin and Fetch Metadata for browser-auth routes. For cookie-authenticated refresh/logout, verify the CSRF cookie/header/MAC/**session ID equality** before state mutation. The initial login/register/Google exchanges use Origin/Fetch Metadata and rate limits, not an existing refresh-cookie credential.
2. Verify refresh token format, permitted `kid`, constant-time MAC. MAC failure or malformed input -> generic 401 with **no family revocation**. Retrieve session/user, verify ACTIVE, session epoch and both idle/absolute expiry.
3. Single-document compare-and-swap (`sessionId`, ACTIVE, current generation/digest, issued epoch, expires future) installs a **single successor verifier** and extends idle up to absolute expiry. One success; zero concurrent duplicate successes.
4. If CAS fails, distinguish revoked/expired/epoch-mismatch (401 normal) from **MAC-authenticated older generation for the same still-active session** (security replay -> revoke that session/family and audit). Never let an arbitrary invalid MAC revoke a victim. Future-generation/wrong-digest authenticated inconsistencies fail closed and audit. No automatic blind refresh replay.
5. Browser performs a single-flight refresh across tabs where supported (Web Locks + BroadcastChannel, conservative fallback). On lost response/reload, **strict rotation may require user to reauthenticate**; classify this operationally as uncertain replay evidence, not proven theft. Never create two active tokens or disable reuse detection to hide network failures.
6. Every protected request checks user status, current epoch and session status; logout revokes the correct session; logout-all/reset/unlink/role change/suspension/deletion bump epoch. `logout` chooses the **refresh cookie + CSRF** as primary if present; an **expired** attached Bearer cannot block logout, but a valid Bearer for a different session causes 403, **no server revocation and no cookie clearing**; the client reports session mismatch without silently clearing a live cookie. Bearer-only logout can revoke its `sid` when no refresh cookie exists; no other user's session can be affected. Session revoke on nonexistent and foreign targets consistently returns 404.

### 5.3 Key management and breach response

Validate JWT signing key, refresh HMAC keyring and CSRF keyring at production boot. Explicit `kid` version selection; do not allow unknown `alg`/`kid`, unsafe default keys or automatic generation in a persisted production environment. Planned rotation: stage new verification key, switch issuer, retire previous key after last credential expiry. On secret compromise, disable old signing/verifier key and invalidate relevant user sessions or all sessions; record an operator incident. No JWT secrets or token raw strings in logs.

## 6. Proxy, browser and request security

**Preferred Pages→Render candidate:** Pages Function forwards only `/api/v1/*` to configured Render upstream; strips any incoming `X-Roundset-*`, `X-Forwarded-*` and other untrusted internal identity headers. It injects `X-Roundset-Edge-Auth` containing a high-entropy deployment-shared secret and `X-Roundset-Client-IP` derived from the trusted Cloudflare request metadata. Express validates the secret via constant-time comparison **before auth rate-limit identity is computed**, and rejects direct-to-Render `/api/v1/auth/*` and other non-health API traffic without valid edge authentication. Do not log the edge secret. TLS must remain end-to-end. Health probes without Origin/edge authentication remain functional and non-sensitive. Phase 10 signed webhooks will use a separate explicit, verified ingress exception contract (never disable auth broadly).

**Ingress and proxy defaults:** `INGRESS_MODE=LOCAL` is forbidden with `NODE_ENV=production` (startup fails). `PAGES_PROXY` requires TLS origin, two configured high-entropy edge secret slots (`current` and optional `previous` with bounded rollover), constant-time compare, authenticated `X-Roundset-Client-IP`; set Express `trust proxy=0` and **never trust raw `X-Forwarded-For`** for rate limits. `SINGLE_ORIGIN` serves React and API on Render and does not require edge header; default `trust proxy=0` with global/account limiter fallback; only enable exact Render ingress hop-derived IP after live anti-spoof verification. `LOCAL` only for loopback development. Pages Function must build upstream URL from a configured fixed host/path allowlist, enforce `redirect:'manual'` (reject unexpected 3xx rather than forwarding edge secrets), strip hop-by-hop `Connection`, `Proxy-*`, `Transfer-Encoding`, and caller supplied `X-Forwarded-*`/`X-Roundset-*`, preserve separate `Set-Cookie` headers, and not leak origin credentials in redirects/logs. Health endpoints are exactly `/api/v1/health/live` and `/api/v1/health/ready` and remain no-Origin/no-edge public.

`X-Roundset-Edge-Auth` is an **upstream ingress proof only**, not user authorization. Express must still validate Bearer/role/ownership/CSRF. Do not trust caller Origin, Host or XFF as rate limiter identity. If no trustworthy IP exists, use a conservative `unknown` bucket plus per-account/global limits. Set `INGRESS_MODE=PAGES_PROXY|SINGLE_ORIGIN|LOCAL`; validate mode and proxy hop settings at boot. Single-origin Render is the approved fallback and gets separate no-header trust tests. Before release, prove Cloudflare multi-`Set-Cookie`, `__Host-` cookies, `Origin`, `Cache-Control: no-store`, and browser refresh after reload work; otherwise use the documented fallback without paid infrastructure.

`apps/api/src/core/security.ts` presently allows requests with no `Origin` to pass and lacks `X-CSRF-Token` in CORS allowed headers. This is acceptable for current public health endpoints, but **must be extended before mounting Phase 2 sensitive routes**. Missing/invalid Origin on authentication mutations fails; non-browser management APIs are separate and explicitly authenticated. Keep health liveness/readiness behavior unchanged. API Helmet CSP is **not** equivalent to a CSP on static HTML served by Cloudflare Pages; the actual web host must deploy a restrictive CSP and tested Google-popup-compatible COOP (do not assert that an existing Google popup currently fails—there is no implemented auth UI yet). React rendering of user content must not enable unsafe HTML execution.

## 7. OTP, rate limiting, email and zero-cost controls

- OTP digits: CSPRNG six-digit, purpose-bound keyed digest, five-minute TTL, maximum five guesses, one active challenge per purpose/subject. **Claim an attempt slot atomically before digest comparison** (conditional `findOneAndUpdate` with `attempts<5`, current generation, accepted delivery, issued/sent state, future expiry; `$inc attempts`). Enforce in both pending-registration verification and recovery/link/contact challenge verification. No concurrent sixth request may even evaluate its OTP guess; consuming a correct proof still requires a single generation-matching transaction. Recovery stores `userId`, password identity `_id`, `identityVersionAtIssue`; after a password or identity change it is stale even before OTP expiry. Authenticated LINK_PASSWORD/PHONE_VERIFY challenge slot digest includes `userId` to prevent cross-user overwrite. `deliveryState` is `PENDING|ACCEPTED|FAILED`; verification requires ACCEPTED. Always check wall-clock expiry in DB predicates; TTL deletion is garbage collection, not validity.
- For registration, challenge is part of pending record and browser-bound to `registrationId`+nonce; other purposes use unique atomic challenge slots. Resend uses conditional generation swap and invalidates older code. Never hold a DB transaction open across a Brevo HTTP call. If provider accepts delivery but the subsequent state update fails, user receives a safe resend/retry UX rather than unauthorized verification. No fake "email delivered" claim from HTTP acceptance alone.
- Argon2id initial parameter floor: 19 MiB, 2 iterations, parallelism 1, measured and tuned under actual Render Free resource constraints. Initial **design ceiling**: 2 concurrent Argon2 operations, queue up to 8, queue wait up to 3s; fail fast with 429/503 when exhausted. Unit and bounded load tests must validate memory/CPU rather than guessing crash rates.
- Cheap in-process pre-DB flood shedding protects limited Atlas throughput; persistent Mongo per-principal/per-operation counters remain authoritative for credential brute force across restarts. **Exact per-endpoint initial default caps appear in contracts §4.4**, including a shared durable email registration/resend bucket and replacement cooldown. Unknown email/password follows a safe dummy-hash path within the same bounded hash budget, and outward responses are uniform where account proof is absent. Email sends are capped through atomic **pre-send increment**, crash-safe UTC-day `emailSendBudget` counters: ≤180 general and ≤60 password-recovery attempts, total ≤240/day versus published 300/day. Unknown send result still consumes budget; never refund uncertain sends or retry unboundedly. Never auto-purchase or use paid fallback when exhausted.
- Public `/auth/register` and `/auth/password/forgot` must never return recipient-dependent 503: global unavailability is evaluated **before lookup** and applied uniformly, and an actual provider failure stays hidden behind the same generic 202 response with an audited delivery-failure state. Timing differences from conditional provider calls require a bounded measured response policy; no unproven constant-time claim. Without CAPTCHA, a determined distributed actor can still drain the reserved email budget; this is an explicit limited-capacity residual risk, not an observed exploit and **not authorization to add a new provider**.
- Real email on Brevo Free is **unvalidated**: sender identity, compliance and inbox delivery must be tested at ₹0 before public email verification is advertised. Free-domain senders may be replaced/rejected. This is a **deployment gate**, not an asserted current breach and not permission to buy a domain. Development mock email must visibly remain mock; production refuses mock email provider. SMS remains mock/development; real SMS needs separately authorized credits.
- Atlas Free current published maximum 100 reads/writes per second; Cloudflare Pages Functions request allowance and Render Free memory/CPU constrain expected load. These are capacity limits, not evidence of an observed DoS. Do not drop durable revocation checking without a separate design review. Rate/cost evidence is required at integration and deployment gates, never assumed from short tests.

## 8. RBAC, profile, deletion, audit

### Deletion state and cleanup safety (v1.2 clarification)

Entering `PENDING_DELETION` immediately denies password and Google exchanges, increments `sessionEpoch`, rejects reset/registration email workflows uniformly, and schedules external Firebase revocation/deletion through an idempotent operator-controlled purge runbook. **Never release `emailNormalized` or the linked Firebase UID while a Firebase delete/revocation step has failed or is unverified.** Preserve the tombstone/mappings until Firebase user deletion succeeds, then remove local authentication identities and associated secrets, and only then anonymize user and release canonical email/phone under privacy policy. Old credential-version-bound recovery challenges cannot act on a different principal that later acquires a released address. No paid background worker is required to state or test this sequencing.

- Roles `CANDIDATE|ADMIN` persisted on `users` only, default candidate. Identity/token role claims and profile edits cannot upgrade privileges. Admin bootstrap: explicit verified user ID one-time operator CLI, reason and audit event. No automatic promotion from `.env.example` email. Phase 10 admin console/API still unimplemented.
- All role/status changes increment session epoch; admin authorization reads persisted current role. ADMIN session TTL is bounded to 12h idle/24h absolute and matched to both refresh/CSRF cookies; require recent step-up for destructive future admin actions. Refuse self-deletion of the sole administrator.
- `PATCH /me` allows bounded preferences and displayName; consent cannot be overwritten with arbitrary client version. Server publishes accepted policy version; consent record carries version/time and append-only evidence. No role, plan, VIP, or verified-status mutation.
- Consent acceptance is append-only: every accepted policy version creates an immutable `CONSENT_ACCEPTED` audit record (`eventId`, `userId`, `policyId`, `consentVersion`, server `consentAt`) in the same transaction as the latest user consent fields. Do not pretend `users.consentVersion` alone represents history. Export all authorized events for the account; apply declared retention/purge policy.
- `GET /me/data-export` is a bounded synchronous self-export of Phase 2 profile/identity metadata/consent events; never password hashes, token digests, OTPs or other users' records. Additional domains must register export/delete handlers when implemented; never paywall access/export/delete.
- `POST /me/account/delete` requires recent action-bound step-up and explicit confirmation; mark `PENDING_DELETION`, bump epoch and revoke all sessions; client loses access immediately. A documented idempotent purge job/operator CLI removes identities, session secrets, phone contact and user PII, handles Firebase Admin UID deletion/revocation and clears ownership indexes in safe order. If external Firebase cleanup fails, keep a non-reprovisionable tombstone/retry state rather than silently recreate the account. A production deletion SLA/retention window must be verified before claiming automated completion on free hosting. Never depend on a paid cron job.
- Audit logs contain identifiers/outcomes/reasons and minimal pseudonymous metadata, no secret, raw email/IP, raw media or full UA. Preserve deletion/security proof only for a defined lawful retention purpose and make the policy explicit before release.

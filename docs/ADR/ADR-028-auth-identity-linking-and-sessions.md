# ADR-028 — Roundset identity, authentication and session security (Phase 2)

**Date:** 2026-11-22  
**Status:** Proposed for project-owner D3 approval; becomes accepted upon merge of the documentation-only PR.  
**Scope:** Phase 2 identity/auth design, not implemented code.  
**Supersedes:** Inconsistent Phase 2 auth details in the older baseline; retains the core decisions of ADR-018, ADR-023, ADR-027.

## Context and constraints

Roundset needs independent Express/MongoDB password auth plus Firebase Google Sign-In without allowing email-only identity merges. The same Roundset user must own its access and refresh sessions. This is a portfolio project with a strict ₹0 non-SMS operating constraint; the existing modular MERN stack, no Redis/microservices, and owner-controlled atomic agent tasks are unchanged. Phase 1 contains health/foundation only; no auth implementation exists.

## Decisions

1. **Identity ownership.** `users._id` is the sole principal. `authIdentities` binds exactly one password credential and/or one verified Firebase-Google UID. Unverified signup lives in `pendingRegistrations`, never as a live account or owned password identity. Registration OTP verification requires browser-bound nonce and only activates the password hash from its own pending attempt inside a Mongo transaction. No OTP-only login.
2. **Google linking and reauth.** New Google identities require valid, verified Firebase Admin proof; linking requires matching canonical verified email plus recent proof of both Roundset factor and target Google account. No automatic account merges by email. Sensitive actions require single-use, hash-at-rest, action/target/method/epoch/version-scoped `reauthTickets` atomically consumed with protected mutation. Last-factor unlink is blocked by shared `users.identityVersion` transaction serialization.
3. **Passwords and OTPs.** Argon2id parameters and concurrency are bounded; recovery OTP is immutable-principal/credential-ID/identity-version bound and expires within five minutes. Every OTP guess (correct or incorrect) **atomically reserves one of maximum five attempt slots before digest comparison**, including pending-registration and verification-challenge operations, with generation/expiry checks. OTP purposes and protected mutations remain isolated. A stale OTP cannot change a replaced credential or later email owner.
4. **Sessions and CSRF.** Memory-only short-lived app JWT with persisted session/epoch checks. Rotating opaque `r1` refresh in Secure HttpOnly host-only cookie; MAC-authenticated replay detection and atomic single-successor CAS. Session-bound signed readable CSRF cookie is required for cookie-authenticated refresh/logout with same remaining TTL (candidate 7d idle/30d absolute; admin 12h idle/24h absolute). Refresh MAC and **separate digest HMAC** keys require versioned retention for active sessions or an explicit global reauthentication event on rotation. `logout-all` and sensitive credential/role/status changes invalidate active Roundset sessions.
5. **Browser/edge.** Strict Origin and Fetch Metadata; nonce-backed pre-session verification uses an explicit exception to session-bound CSRF. In `PAGES_PROXY` mode edge→Render authentication is required; fail closed to direct Render auth attempts. `LOCAL` is prohibited in production. A single-origin Render fallback is permitted only by documented approval. Production deployment must prove cookies/CSP/COOP and trusted forwarding behavior.
6. **Abuse, privacy, zero-cost.** Durable per-email registration/reset rate limits apply **before user existence lookup** for both known and unknown accounts. General email quota ≤180/day and recovery-only quota ≤60/day are guardrails, **not proof of Brevo's reset clock**; verify provider allowance and reset boundary before live emails and gate any boundary mismatch. `LINK_PASSWORD` uses general quota. Audit every consent acceptance **including registration and first Google provisioning** immutably (`eventId`, `userId`, `policyId`, `consentVersion`, `consentAt`) alongside latest user consent, self-exportable under retention rules. Explicit status-preserving deletion prevents Firebase reprovisioning. No production mock verification or unapproved paid service.
7. **Interface and ownership.** The [`auth.v1` contract](../phase2/P2_AUTH_API_CONTRACTS_v1.md) is authoritative for endpoint DTOs, error behavior, indexes and acceptance tests. [`execution plan`](../plan/PHASE_02_IDENTITY_EXECUTION_PLAN.md) controls task dependencies: A05a owns meta/refresh/logout/logout-all; A07a owns reauth and password change; A07b owns audited admin seed. No implementation agent may alter these decisions independently.

## Deferred validation / no false assurance

Real Firebase token/security behavior, Atlas replica-set concurrency and indexes, Render-memory Argon2 benchmark, Brevo sender/quota/inbox delivery, and browser Cloudflare→Render cookie handling are **unverified release gates**, not confirmed exploits or completed tests. The application must not claim live email production-readiness until validated at ₹0. A code change requires its own authorized task, independent review and observed tests.

## Consequences and migration

This ADR adds temporary registration, immutable consent-event, session and OTP security state to Mongo; it replaces older broad auth endpoint names/fields where they conflict. The original `docs/API_AND_DATA_CONTRACTS.md` remains the roadmap-wide baseline, but `docs/phase2/P2_AUTH_API_CONTRACTS_v1.md` takes precedence **for Phase 2 auth**. No automatic ADMIN elevation from email placeholder. All `P2-AUTH-*` tasks remain unchecked until accepted with test evidence; only project-owner-approved documentation PR merge may close `P2-DESIGN-01` and authorize a separately scoped first implementation ticket.
